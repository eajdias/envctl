- 2026-08-26 ✅ Quando validar mudanças no envctl: `go build ./... && go vet ./... && go test ./...` + `envctl.exe doctor` (163 checks, meta 0 WARN/0 ERRO) + deploy real com `envctl run shell` do root do repo (porque evidência > afirmação; o doctor cobre manifestos, env vars, configs, skills, LSPs, WSL, temp).
- 2026-08-26 ✅ Quando inspecionar estado do OpenCode na máquina: `envctl run cleanup` (configs legados, tool-output >10MB, scratch `C:\temp` >24h) + `envctl run shell` (re-sincroniza configs e remove stale) antes de mexer manualmente (porque o provisioning é idempotente e deixa a máquina alinhada ao repo).
- 2026-08-28 ✅ Quando criar skill global nova: criar em `configs/skills/<nome>/SKILL.md` + registrar em `manifests/skills.yaml` (lista ordenada) + espelhar em `~/.config/opencode/skills/<nome>/` (porque o manifest é embutido no binário em BUILD time — sem rebuild, `envctl run skills` não conhece a skill nova; o espelho manual a ativa imediatamente no opencode local e o próximo build/release a distribui).
- 2026-09-25 ✅ Quando uma skill é servida aos DOIS agentes (o envctl não tem escopo por agente em `entity.Skill`, só `OS`), documente uma seção por runtime (`## OpenCode V2` e `## CommandCode`) e trave com teste de conteúdo POR SEÇÃO (termo exigido numa coluna e proibido na outra) — porque "limpar" o arquivo inteiro quebra silenciosamente o outro agente e nenhum teste genérico acusa.
- 2026-09-26 ✅ Para testar se o loader de um agente tolera uma chave de frontmatter **sem gastar call de modelo**: crie uma skill de sondagem descartável (`~/.config/opencode/skills/zzz-probe/SKILL.md`), mude só o frontmatter, e use a linha `message="skills rescanned"` de `~/.local/share/opencode/log/opencode.log` (o watcher reescaneia em ~6s) como sinal. **Sempre valide o sinal com um controle** e cuidado: essa linha loga DESCOBERTA (o arquivo existe), não PUBLICAÇÃO — `description: ""` ou frontmatter quebrado continuam aparecendo nela; só o arquivo removido some (controle que funciona). Prova de "ainda é publicado ao modelo" exige o catálogo model-facing (`opencode run -p`) ou leitura do binário (`grep -a -o -E '.{60}autoinvoke.{90}' /usr/bin/opencode`).
- 2026-09-26 ✅ Antes de criar skill nova, aplique o filtro: ela entra no catálogo **só** se contiver algo que o modelo não faria sozinho (preferência do usuário, procedimento não-óbvio, armadilha já paga). Conhecimento de ferramenta/linguagem/domínio vira `code-playbooks/references/<tema>.md`; comportamento obrigatório vira linha do `AGENTS.md`; conhecimento do produto envctl fica no repo. Motivo da regra: medido com `cmdc -p` que 50 skills custavam ~6,4k tokens/turn e, no budget default do CommandCode, o catálogo degrada para nome+location e a auto-ativação **deixa de acontecer** (0 `activate_skill`); 12 skills cabem no default.
